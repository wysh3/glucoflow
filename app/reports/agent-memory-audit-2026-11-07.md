Two nearby limitations matter for day-to-day quality. A broad model read can see only the first 12 encounters, 16 orders and 12 events even though a workspace allows 30 encounters and 50 orders. Exact internal IDs can target later records, but the tool lacks a targeted lookup by the demo codes visible to staff. Also, chat history is forwarded as text, so a follow-up such as “monitor that one” cannot reliably recover a previously selected ID. These are retrieval and context gaps that a model switch alone leaves in place. Add exact code lookup and an explicit, revalidated selected reference before increasing prompt size. ## What to take from Anthropic’s work

Anthropic defines agent memory as experience retained across sessions through context that the agent can retrieve again. It distinguishes that from model training, in-session learning and context compaction. Its hierarchy starts with searchable transcripts, adds notes about salient experiences, organizes reusable material into representations such as wikis, and promotes a small subset into starting context. Offline reflection can check notes against original records and revise them before reuse. [The components of agent memory](https://www.anthropic.com/research/components-of-agent-memory)

Their findings make two choices relevant here. Memory helps when the stored representation captures a tested rule that the current screen cannot tell the agent. It can hurt when it is stale, too large, or based on an untested guess. Across their examples, performance varied by task and model, source search still mattered alongside a wiki, and concurrent edits to a shared representation erased evidence before they separated the write paths. Those were Claude evaluations on database tasks, game play and document work. They provide design hypotheses for GlucoFlow, with no measured healthcare or Luna/Sol transfer result. [Anthropic evaluation and caveats](https://www.anthropic.com/research/components-of-agent-memory)

Hermes itself provides curated profile notes, past-session search, procedural skills and optional review gates for skill edits. Those are appropriate references for capture, retrieval and versioning. The current integration uses an app-controlled database boundary because shared free text or a writable profile cannot enforce encounter authorization, authoritative evidence, scoped publication and rollback on its own. Model-assisted reflection can draft a narrow typed candidate in a separate job. An application review transaction can publish it after independent checks. ## A minimal governed learning loop

Use one recurring problem from the existing simulator, **handoff for a collected specimen with unverified LIS receipt**. A shift coordinator reviewing synthetic Patient A has to hunt for whether the lab feed is fresh and who owns the missing handoff. Staff records a structured correction to the presentation. The reusable procedure puts the current evidence state, accountable role and source-opening action together at the top of a handover when a matching active order has this pattern. A disconnected or stale source renders status unknown. A matching receipt, cancellation or scope mismatch suppresses that item. This changes what information appears at handoff and how easily staff can verify it. The underlying source requirements and clinical actions stay with their existing owners.

| Stage | Smallest useful addition |
| --- | --- |
| Capture | Add an authenticated **Flag a workflow gap** action with a fixed reason, workflow family and expected presentation behavior. Save an immutable episode receipt containing actor, workspace revision, trigger, scoped source-event links and captured feed freshness. Keep patient details behind the encounter authorization boundary. |
| Distill | On explicit review request, a worker projects only operational predicates and outcome codes from eligible episodes, including successes, failures and exceptions. A model may select or propose a typed recipe from an enum. Independent code checks every cited event and claim against captured evidence. A single episode can create a review candidate. Promotion should require a second independent corroborating episode and a held-out validation pass. |
| Test | Compile the candidate to the existing renderer and run versioned fixtures with fresh timestamps and unseen IDs. Persist artifact digest, scope, source-evidence digest, fixture revision, failures and prior-version comparison. Approval checks the exact digest that passed. |
| Publish | Give the typed procedure an immutable version, workflow family, clinic/unit scope, reader roles, reviewer identity, expiry and rollback target. First prove transfer across two owner-authorized synthetic workspaces in one clinic. Before allowing different staff to share a version, add real server-resolved unit membership and publishing capability. The client-side simulation role is insufficient for that authority. |
| Retrieve for B | Query active approved versions by clinic, unit or synthetic-owner scope, role, workflow key and expiry. Match current B predicates on the server using B’s own evidence. Send only the bounded procedure ID, version and operational rule. Return the applied version and B’s exact source references in the handover. A’s identifiable details and raw transcript are absent from B’s retrieval projection. |
| Monitor and revoke | Record version, applicability, acceptance or correction, elapsed workflow effort and stop condition. Retire or supersede incompatible versions with compare-and-swap or a row lock. Exclude revoked or stale versions at retrieval. Keep review provenance auditable to authorized reviewers and apply explicit retention to detailed episodes. |

Reuse the app’s append-only evidence, transactional revision checks and sandbox approval pattern. A typed artifact for the first use case can be smaller than an unstructured skill. Candidate and active rows can hold a fixed trigger, allowed presentation variant, required HIS/LIS evidence, permitted role, source-open action and version lineage. Start with structured lookup rather than embeddings. That keeps the application able to explain why a procedure applied, and whether it came from staff feedback or from the default workflow.

The demo that establishes transfer uses a fresh B workspace with distinct source IDs and a fresh conversation. Compare B on the baseline and the promoted version while holding B’s evidence constant. Show the applicable version and improvement on the same handover, then revoke it and show the baseline behavior again. Add a second actor with independently verified unit access only when cross-staff reuse is authorized. A seeded fixture and another patient’s result cannot substitute for B’s evidence. The learning boundary is coordination procedure. Diagnosis, clinical prioritization, dose, treatment, referral timing and patient-specific outcomes stay outside the learned procedure.

## Evaluation and latency

1. **Separate evidence, memory and model evaluations.** Use deterministic fixture tests for permissions, event relations, completion, and compiled playbook behavior. Use a local protocol double to prove both transports preserve the tool allowlist, typed outputs, no fallback and request caps. Only a credentialed live paired evaluation can measure model decisions. Split episode data by scenario family and synthetic ward so curation never sees the held-out cases.
2. **Include unseen and adversarial cases.** Cover unknown formats and aliases, duplicate names, a relevant encounter beyond the broad read cap, current versus expired playbooks, cross-tenant or revoked access, mismatched specimen receipt, stale feed, delayed/backdated correction, reordered and duplicate events, order cancellation, role switching, concurrent approval and rollback, a mixed clinical/operational query, and injection text in a synthetic field or past message. Include replayed positive examples, conflicting episodes, and superficially similar B scenarios where the recipe should abstain.
3. **Score behavior before style.** Prespecify exact intent, scoped IDs, actionable proposal shape, source references, freshness and abstention. Count tenant/encounter leakage, invented evidence, clinical advice or unauthorized changes as hard failures. Measure correct applicability and rejection rates, task completion, citations, reviewer correction rate and elapsed staff task time. Compare B with memory off/on and prior-version rollback using the same sources. Report sample sizes and uncertainty. Generalization and productivity remain hypotheses until measured.
4. **Run a bounded model comparison after approval.** Use Luna Chat Completions/none as shipped baseline. Add Luna Responses/none to isolate transport, then Luna Responses/low and Sol Responses/low for a like-for-like model comparison. Use the same evidence, tools, prompts, caps and blind grader. For an initial 12-case matched low-effort screen, at most three outbound calls per case and model gives 72 total. If the harness enforces 4,000 input and 650 output tokens per call, estimated maximum standard charges are about $0.55 for those two arms, before deployment or provider extras. That estimate assumes uncached short-context pricing and excludes transport-control arms. The current byte cap is insufficient to guarantee the 4,000-token budget. Reserve the measured provider call and token ceiling before starting.
5. **Decompose wall time.** Use monotonic durations for client submission, API auth/DB snapshot, bridge, sidecar admission, subprocess launch/import/init, each provider request, each local tool/reduction, and API persistence/response rendering. Keep only timing, size, usage, result and model-configuration metadata under a short-lived correlation ID. No prompts, patient labels, tool arguments or source payloads in telemetry. Measure cold replica, warm replica with new process, and warm preloaded worker separately. Report p50, p95, deadline-censored attempts, provider calls per success, input/cached/output/reasoning tokens and cost per accepted answer.

Measured release baselines are **19.1 s** for a live Luna turn from the Linux container under local emulation, a hosted timeout at **30.198 s** and a subsequent hosted success at **44.203 s**. The latter runs with 0.25 vCPU and 0.5 GiB allocated to Hermes. The timeout led to a 60-second subprocess deadline and 65-second bridge deadline. The conversation loop retains its 25-second limit and three-call cap. These are three recorded outcomes across different conditions. They do not isolate provider time, CPU startup or a model speed distribution. [Deployment evidence](care-deployment-2026-11-07.md) · [Sidecar process limits](../hermes/server.py#L19) · [Bridge deadline](../apps/api/src/care/chat.ts#L115)

Measure import time first. If it dominates, compare an isolated preloaded worker or more CPU with the same authorization and cleanup guarantees. The current model loop may perform read, response intent and a final acknowledgement. The adapter renders the accepted tool output and discards acknowledgement prose. Evaluate a verified stop after accepted response via an upstream-supported hook, preserving the source, budget and completion checks. Keep heavier episode synthesis outside the interaction path so teams can continue working while a draft is prepared.

## Implementation and fresh verification

The care reader now supports exact demo codes, exact names and specimen identifiers. Ambiguous lookup returns a clarification without selecting an encounter. Literal notes carry the synthetic encounter record as provenance, while source citations identify independently recorded HIS/LIS events. Handover identifies the open task owner where one is recorded. For a matching approved clinic skill, the worker stages the reviewed `source-handoff/SKILL.md` in the request's private Hermes profile and resolves it through upstream `skill_view(preprocess=False)`. The application still verifies B's current evidence, skill version and permissions before creating an approval request. ### Native document and record planning workflows

Pinned upstream `read_file` supports PDF text extraction through anydoc. For a scan, its read path can report pages needing OCR or invoke separately configured hosted OCR. Its paginated text output lacks GlucoFlow's existing evidence IDs, normalized page coordinates, and review contract. Upstream vision accepts base64 image content natively. Its general vision tool can also use an auxiliary model. The separate upstream video analyzer uses a video-capable auxiliary route with a larger size and time budget. OpenAI's Luna card lists image input and has no video modality, and the existing app upload contract accepts PDF, JPEG and PNG. [Pinned PDF extraction](https://github.com/NousResearch/hermes-agent/blob/2bd378ed1b8d6bf2192cb26e0a55ff3091e6bd19/tools/read_extract.py) · [Pinned image and video tooling](https://github.com/NousResearch/hermes-agent/blob/2bd378ed1b8d6bf2192cb26e0a55ff3091e6bd19/tools/vision_tools.py) · [Luna modalities](https://developers.openai.com/api/docs/models/gpt-6-luna)

The new worker transport sends authorized prepared page text, evidence IDs and up to two PNG page images to private `POST /extract`. The sidecar authenticates the worker, checks the audited system prompt hash, resolves the reviewed extraction skill through upstream `skill_view` and runs a genuine upstream `AIAgent` turn with native images. Its transport permits one actual provider call, exact model and JSON response mode, no exposed model tools, and a 4,096-token output ceiling. A native-vision route preserves the supplied images and bypasses Hermes' auxiliary image-description path. The worker reserves each request in the durable budget ledger, handles bounded repair and validates the returned draft against the original evidence. Authorization, private storage, preparation/OCR, page transforms and human approval remain application services. Private `POST /record-plan` uses the same one-call runner for the retained app guide and record retrieval planners, with their own pinned prompt hashes and a 900-token ceiling.
