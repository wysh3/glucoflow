## Minimal native extraction seam

1. The API still authenticates the patient or clinic actor and validates the ordered upload manifest. GlucoFlow accepts PDF, JPEG and PNG with a 15 MiB file or photo-batch cap and up to ten pages/photos. The worker leases the job, validates the object bytes, handles duplicates and prepares source pages and evidence. [Upload contract](../packages/contracts/src/uploads.ts) · [Upload routes](../apps/api/src/routes/uploads.ts) · [Worker job](../packages/extraction/src/document-job.ts)
2. Preserve the existing `ExtractionProvider` contract and the durable reserve/reconcile calls. The production provider can dispatch each prepared batch over authenticated private `/extract` to the pinned `AIAgent`. The proposed interface accepts up to two prepared inline PNGs and the exact trusted extraction prompt. It executes at most one paid request per POST. The worker still controls the document's batch ordering, retries, partial coverage and retry budget. The authenticated server route supplies scope. Provider credentials belong to the sidecar. [Provider interface](../packages/extraction/src/types.ts) · [Existing budget and dispatch](../packages/extraction/src/providers/openai-compatible.ts)
3. Preserve deterministic validation of evidence, identity, values, units and dates. Persist a draft tied to the authorized document version and actual provider usage. Review and publication continue through the transactional app workflow. A synthetic release check should verify the `hermes` provider provenance and draft facts against the original source before a human publishes. [Pipeline](../packages/extraction/src/pipeline.ts) · [Extraction contract](../../docs/mvp/04-extraction-engine.md)

The existing Luna extraction path uses Chat Completions with low reasoning and no function tools. The minimal native core adapter can preserve that output contract and single-call budget. A model-selected Hermes function on Chat Completions requires explicit `reasoning_effort: "none"` for Luna, or a separate Responses adapter. A later tool-enabled path must preserve the same evidence and spending gates. Inspect genuine upstream invocation and the outbound call count when verifying native provenance. [OpenAI Luna](https://developers.openai.com/api/docs/models/gpt-6-luna)

The original record companion had separate direct provider calls in `guide/service.ts` and `guide/conversation.ts` at initial inspection. The coordinated implementation assigns these two paths to a private Hermes `/record-plan` route. Verify guide scope and provider invocation separately from the upload worker. ## Hosted topology and release preparation

The active worker `glucoflow-worker--closure` is a Single-revision Consumption app with no ingress. It has a PostgreSQL KEDA rule using the existing scale secret and a 0–1 replica range. The worker uses 0.5 vCPU and 1 GiB. The prepared release adds the same pinned Hermes image to the worker replica at 0.25 vCPU and 0.5 GiB. The combined 0.75 vCPU and 1.5 GiB is a documented Consumption allocation. The worker calls `http://127.0.0.1:8642`, and only the sidecar references the existing worker model secret. Its app-level service token is independent of the API app's token. The KEDA rule wakes both containers for document work, and the API's separate Hermes sidecar continues to serve interactive work. [Azure multi-container resources](https://learn.microsoft.com/en-us/azure/container-apps/containers) · [Azure scaling](https://learn.microsoft.com/en-us/azure/container-apps/scale-app)

This avoids cross-app ingress, keeps model startup and processing within the document worker replica, and keeps the public API outside the worker's queue and probe lifecycle. Compute can scale to zero as before. The added sidecar increases resources during document processing. Keep the worker startup gate tied to extraction readiness, or retry a transient sidecar startup failure through the existing durable policy.
